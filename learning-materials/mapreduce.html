MapReduce

大数据四件套 ② · 属于「分布式计算」模块 · 建议 45–60 分钟学完并做完练习

先搞清楚它解决什么问题：数据太大，一台机器装不下、算不完。MapReduce 的做法不是"造一台更快的机器"，而是把同一个简单函数复制到几百台机器上，让每台只处理一小块数据。你要写的只有两个函数——map 和 reduce；至于怎么切数据、怎么分发、某台机器挂了怎么办，全部由框架负责。

MapReduce 速览

维度内容
它是什么一种分布式计算的编程模型：把一次计算拆成 Map 与 Reduce 两个阶段，框架负责分发、排序与容错
谁提出的Google 于 2004 年发表的论文《MapReduce: Simplified Data Processing on Large Clusters》（Dean & Ghemawat，OSDI'04）；Apache Hadoop 是它的开源实现
唯一数据形态从头到尾只认 <key, value> 键值对，输入是键值对，输出也是键值对
并行单位输入被切成 N 个分片（InputSplit），一个分片启动一个 Map 任务；Reduce 任务的数量由用户在作业里指定
典型任务词频统计、日志清洗、倒排索引、按维度分组聚合、大表连接（join）
不擅长需要多轮迭代的计算（机器学习训练、图计算）、交互式即席查询、数据量小到单机就够的场景

四个必须理解的点

1

一切都是键值对

记住这条官方表述：框架只处理 <key, value> 对。

MapReduce 框架把作业的输入看成一组 <key, value> 对，产出的也是一组 <key, value> 对，而且输出的类型可以和输入完全不同。整条链路上的类型是这么走的：

(input) <k1, v1>  →  map  →  <k2, v2>  →  combine  →  <k2, v2>  →  reduce  →  <k3, v3>  (output)

在 Hadoop 里，key 和 value 都必须能被框架序列化（实现 Writable 接口）；此外 key 还必须能比较大小（实现 WritableComparable）——因为框架要给 key 排序，排序是后面 Shuffle 能"把相同 key 聚到一起"的前提。

为什么非要键值对？因为"按 key 分组"是整个模型唯一的汇聚手段。Reduce 之所以能把散落在几百台机器上的数据合并起来，靠的就是"key 相同即同类"这条约定。没有 key，就没有办法决定哪条数据该送到哪个 Reducer 去。
2

分片：并行的起点

一句话：一个 InputSplit 对应一个 Map 任务。

InputSplit 表示"交给单个 Mapper 处理的那一份数据"。InputFormat 负责三件事：校验输入、把输入文件切成若干逻辑 InputSplit、再提供 RecordReader 把字节流翻成一条条记录喂给 Mapper。官方原话是：框架为 InputFormat 生成的每一个 InputSplit 派生一个 map 任务。

对文件型输入，默认按文件总字节数切分；HDFS 的块大小（blocksize）被视为分片大小的上限，下限可通过 mapreduce.input.fileinputformat.split.minsize 配置。这里正好接上 hdfs.html——HDFS 负责把大文件切成块存起来，MapReduce 负责在这些块所在的位置上就地计算。

数据本地性（最重要的一条设计思想）：通常计算节点和存储节点是同一批机器，MapReduce 框架与 HDFS 跑在相同的节点集合上。这让框架能够把任务调度到数据已经存在的节点上执行，从而在整个集群上获得非常高的聚合带宽。这就是常说的"移动计算比移动数据便宜"。
3

Shuffle：MapReduce 的心脏

这是框架做的，你的代码里看不到它，但它往往是最耗时、最耗网络的一步。

官方把 Reducer 的工作分成三个阶段：shuffle、sort、reduce。

阶段做了什么备注
ShuffleReducer 通过 HTTP 把所有 Mapper 输出中属于自己的那一个分区抓过来跨机器传输，最贵的一步
Sort按 key 排序并分组——不同的 Mapper 可能输出了同一个 key，框架在此把它们汇到一起与 shuffle 同时发生，边抓边归并
Reduce对每个 <key, 值的列表> 调用一次 reduce()输出通常直接写进文件系统

决定"哪个 key 去哪个 Reducer"的组件叫 Partitioner，默认实现是 HashPartitioner（对 key 取哈希）。分区数恒等于 reduce 任务数。

Reduce 任务数怎么定？官方给出的经验值是 0.95 或 1.75 乘以（节点数 × 每节点最大容器数）。取 0.95 时所有 reduce 可以立刻启动；取 1.75 时快的节点会跑完第一轮再接第二轮，负载更均衡。如果根本不需要归约，把 reduce 任务数设成 0 也是合法的——此时 map 的输出直接落到文件系统，且框架不会排序。
4

Combiner：可选的加速器

作用是在 Mapper 端先做一次局部聚合，减少 Map 到 Reduce 之间要传的数据量。

Combiner 通过 Job.setCombinerClass() 指定，是一个可选组件。以词频统计为例，如果某个 Map 任务的输出里 hadoop 出现了 4 次，不加 Combiner 就要把 4 个 <hadoop, 1> 都传过网络；加了 Combiner 之后，本地先合成一个 <hadoop, 4>，只传 1 个。

易错：Combiner 不是任何场景都能加。它要求运算满足交换律和结合律——求和、求最大值、求最小值可以；求平均值不行（详见后面「易混辨析」第 4 组，附实跑数字）。另外框架只保证 Combiner 可能被调用，不保证一定被调用，所以正确性绝不能依赖它。

核心机制：一次作业的完整数据流

图怎么看：从上往下读。最上面三个绿色块是被切开的数据，每一块起一个 Map 任务——三个 Map 跑的是同一份代码，只是喂进去的数据不同，而且它们之间互不通信，这正是能随意横向扩展的原因。接着所有 Map 的输出汇进中间那个贯穿全宽的绿色块，也就是 Shuffle：它按 key 排序、把同 key 的 value 归成一组、再按哈希分给不同的 Reduce。下面三个蓝色块是 Reduce，同一个 key 只会出现在一个 Reduce 里——这是 Reduce 能够"收拢"的前提。最后每个 Reduce 各写一个小文件，所以有几个 Reduce 就有几个输出文件。最下面那行是类型链，注意 <k2,v2> 变成 <k2,[v2,v2,…]> 的那一刻，就是 Shuffle 干的事。

应用场景：统计全站热点词

场景：假设你是某新闻网站的数据工程师，要找出全站 10 亿篇文章里出现次数最多的词，用来生成热点词云。文章总量是 TB 级，单机跑不动。你写两个函数交给集群：map 负责把每篇文章切成词、每个词吐一个 <词, 1>；reduce 负责把同一个词的所有 1 加起来。中间怎么分发、怎么排序，你一行都不用写。

图怎么看：按 ① → ⑥ 的顺序走一遍。关键是第 ④ 步——它把"散在各台机器上的 hadoop"收拢成了一个列表 [1,1,1,1]，第 ⑤ 步才能求和。虚线框的 Combiner 是可选的：本例加了它之后，要跨网络传的键值对从 13 个降到 5 个，而最终 reduce 的结果完全一样（这一点后面有实跑验证）。

用 Hadoop Streaming 亲手写一遍

Hadoop 支持用任意可执行程序当 Mapper / Reducer（Hadoop Streaming）：从标准输入读一行，往标准输出写 key\tvalue。下面两个 Python 脚本就是符合该接口的最小实现——注意 reducer 能这么写，前提正是框架已经保证输入按 key 排好序并分好组。

# mapper.py：从 stdin 读，往 stdout 写 "key\tvalue"
import sys
for line in sys.stdin:
    for word in line.strip().split():
        print("%s\t%d" % (word, 1))

# reducer.py：输入已按 key 排序并分组
import sys
current, total = None, 0
for line in sys.stdin:
    word, count = line.rstrip("\n").split("\t")
    count = int(count)
    if word == current:
        total += count
    else:
        if current is not None:
            print("%s\t%d" % (current, total))
        current, total = word, count
if current is not None:
    print("%s\t%d" % (current, total))

本地用管道模拟一遍（sort 就是在模拟 Hadoop 的 shuffle + 排序）：

$ cat mr_input.txt

mapreduce spark hadoop
big data big data hadoop

$ cat mr_input.txt | python mapper.py

mapreduce	1
hadoop	1
big	1
data	1
mapreduce	1
spark	1
hadoop	1
big	1

big	1
data	1
hadoop	1

$ cat mr_input.txt | python mapper.py | sort | python reducer.py
big	3
data	3
hadoop	4
mapreduce	2

把 sort 去掉会怎样？reducer 会把同一个词的多次出现误判成多个不同分组，输出变成 hadoop 1、hadoop 1、hadoop 1、hadoop 1 这样拆开的结果。这个实验能最直观地说明：Shuffle 的排序不是"顺便做的优化"，而是 Reduce 正确性的前提。

五组易混辨析

① MapReduce 和 Hadoop 不是一回事

MapReduce 是编程模型（一种"先 map 再 reduce"的计算思想，出自 Google 2004 年论文）；Hadoop 是这个模型的开源实现，而且 Hadoop 现在指的是一整套生态（HDFS + YARN + MapReduce 等）。类比：MapReduce 是"菜谱"，Hadoop 是"按这个菜谱做出来的那道菜外加整间厨房"。说"我用 MapReduce 存数据"是错的——存数据是 HDFS 的活儿。

② Shuffle 不是"打乱"，恰恰相反

这个词最容易望文生义。Shuffle 在扑克牌里是"洗牌"，但在 MapReduce 里它的效果是把同类key聚拢——框架抓取各 Mapper 的输出、按 key 排序、把相同 key 的 value 汇成一组。它"打乱"的只是数据的物理位置（从各台机器搬过来），逻辑上反而变得整齐了。记住：shuffle 与 sort 是同时发生的，边抓取边归并。

③ Combiner 不是想加就能加

它要求聚合运算满足交换律与结合律。求和、计数、求最大 / 最小值可以；求平均值、求中位数不行。本地实跑的数字（数据 [2,4] 与 [6]）：

正确做法（传「和 + 个数」到 reduce 再除）：总平均 = 4.0
错误做法（map 端各自求平均再平均）：3.0 与 6.0 → 4.5
两者相等吗： False

真要算平均值，正确写法是 map 输出 <key, (和, 个数)>，在 reduce 端先分别求和、最后再做一次除法。另外框架不保证 Combiner 一定被调用，所以正确性永远不能依赖它。

④ Reduce 的输出不是全局有序的

官方明确写了：Reducer 的输出是不排序的。Shuffle 阶段排序的是 reduce 的输入，不是输出。所以你会得到若干个 part-r-000xx 文件，每个文件内部按 key 有序，但跨文件之间没有顺序保证。想要全局有序的结果，要么只设 1 个 Reduce（牺牲并行度），要么额外做一次全排序作业。

⑤ MapReduce 并没有"被淘汰"，但它确实有边界

它仍然适合一次扫描就能算完的批处理：ETL 清洗、日志统计、倒排索引。它不擅长的是需要反复迭代同一份数据的场景——每一轮迭代都要重新读盘、重新 shuffle，代价极高。这正是后来 Spark 出现的动机（把中间结果放在内存里复用）。本系列的下一份资料会讲 Spark，到时候可以直接对比两者的迭代成本。

动手练习

先自己写，再展开对答案。

练习 1：写出 WordCount 作业中 map 和 reduce 各自的输入 / 输出类型 
map:     <k1=行的起始偏移量, v1=该行文本>  →  <k2=单词, v2=1>
reduce:  <k2=单词, [1, 1, 1, ...]>        →  <k3=单词, v3=总次数>

要点：输入键是什么取决于 InputFormat——用默认的 TextInputFormat 时，key 是这一行在文件中的字节偏移量，value 是这一行的文本；但 WordCount 根本不关心这个输入 key，真正起作用的是 map 自己产出的 <单词, 1>。回到正文：见「一切都是键值对」与「Shuffle」。

练习 2：输入是 ["a b a", "b c"]，写出 map 输出条数、shuffle 后的分组、reduce 的最终结果 
map 输出：[('a', 1), ('b', 1), ('a', 1), ('b', 1), ('c', 1)]   条数 = 5
shuffle 分组：{'a': [1, 1], 'b': [1, 1], 'c': [1]}
reduce 结果：[('a', 2), ('b', 2), ('c', 1)]

要点：map 输出的条数等于单词出现的总次数（5），不是不同单词的个数（3）——这是初学者最容易答错的地方。shuffle 之后才是 3 组。回到正文：见「Shuffle：MapReduce 的心脏」。

练习 3：给 WordCount 加上 Combiner 之后，跨网络要传的键值对从 13 个降到 5 个，为什么最终结果完全不变？ 
不加 combiner 要传：13 个键值对
加 combiner  要传：5 个键值对
reduce 结果是否一致： True

要点：因为加法满足结合律——先把 (1+1) 合成 2 再与别人的 2 相加，和直接把四个 1 相加，结果相同。所以 Combiner 只是"提前做了一部分求和"，不改变语义。反例见辨析 ③：平均值不满足这个性质，加了 Combiner 就会算错。回到正文：见「Combiner：可选的加速器」。

练习 4：判断正误——「Reduce 的输出是按 key 全局有序的」，并说明理由

错误。官方明确说明 Reducer 的输出不排序。被排序的是 reduce 的输入（由 Shuffle 阶段完成）。结果被写成若干个 part-r-000xx 文件，每个 Reducer 一个：单个文件内按 key 有序，文件之间没有顺序保证。要全局有序，要么把 reduce 任务数设成 1（但那样就没有并行度了），要么再跑一次专门的排序作业。回到正文：见辨析 ④。

自检清单

  1. 能说出 MapReduce 的定义，并区分「MapReduce（编程模型）」与「Hadoop（开源实现）」
  2. 能说出整条类型链：<k1,v1> → <k2,v2> → <k2,[v2…]> → <k3,v3>，并指出哪一步是 Shuffle 造成的
  3. 能解释「一个 InputSplit 对应一个 Map 任务」，以及为什么分片大小以 HDFS 块大小为上限
  4. 能说明 Shuffle 做了哪三件事（抓取 / 排序分组 / 分区），以及为什么它是最贵的一步
  5. 能判断某次聚合能否加 Combiner，并说清平均值为什么不行
  6. 能说清「同一个 key 只会进入一个 Reduce」这条保证是由什么组件实现的（Partitioner，默认 HashPartitioner）
  7. 能判断 Reduce 的输出是否全局有序，并给出要全局有序时的两种做法
  8. 能举出 MapReduce 适合与不适合的任务各一个，并说明不适合的原因
