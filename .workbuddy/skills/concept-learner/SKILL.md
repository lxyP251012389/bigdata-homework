# 概念学习资料生成 Skill（concept-learner）

把"如何系统学习一个新概念"沉淀成可复用的流程：理解 → 检索 → 结构化 → 通俗化 → 可视化 → 自检。
任何人给出一个新概念，都能用同一套方法产出质量稳定的学习资料。

## 一、适用场景

- 学到一个新概念（技术名词、课程术语、工具机制），想系统整理成学习资料
- 课程预习 / 复习，需要结构化笔记而不是碎片化搜索结果
- 想要"讲人话"的解释 + 可核查的官方来源，而不是名词堆砌或博客口水文
- 需要自测问题（带反馈）来检验自己是否真的学会了
- 需要可视化图辅助理解抽象机制或多角色交互

## 二、输入信息

| 输入项 | 必填 | 说明 | 默认值 |
|--------|------|------|--------|
| 概念名称 | ✅ | 要学习的概念，如"大模型的上下文" | 无 |
| 输出文件名 | ❌ | learning-materials/ 下的文件名 | 概念英文名的 kebab-case，如 `llm-context.html` |
| 学习深度 | ❌ | `入门` 或 `进阶` | 入门 |
| 重点关注 | ❌ | 希望额外展开的角度，如"与其他课程概念的关系" | 无 |

## 三、生成步骤

1. **理解概念**：明确概念的定义、所属领域、常见使用语境；如有一词多义，先列出主要含义并说明本资料采用哪个。
2. **检索来源**（仅官方）：通过 WebFetch / WebSearch 查找 **2–4 个官方来源**（详见第五节），逐条实际访问验证 HTTP 200 与内容相关，记录 URL 与访问日期。**禁止编造任何来源，禁止使用博客、第三方教程、个人文章。**
3. **结构化组织**：严格按照下方"输出结构"的八个板块组织内容，不得缺项、不得调换顺序。
4. **通俗转写**：第三板块"通俗解释"必须用第三人称、教学式语言（**不是第一人称口吻**），配合"类比 + 类比局限"使抽象概念落地（详见第四节第 3 板块规范）。
5. **设计可视化**：按下方"可视化规范"为第 4、5 板块各配 1 张图——优先 Mermaid 时序图 / 流程图 / 概念图，复杂结构辅以对比表；**配色严格收敛**（最多 2 种语义色 + 中性灰）。
6. **生成 HTML**：输出为**自包含**的 HTML 文件（内联 CSS；Mermaid `<pre class="mermaid">` + CDN），配色收敛（主线蓝 + 强调橙 + 中性灰，无紫 / 青 / 绿），保存到 `learning-materials/<输出文件名>`。
7. **自检**：执行下方"自检清单"，逐项核对，全部通过才算完成。
8. **交付**：把生成的文件展示给用户预览，**明确提醒用户进行人工核查**（核对事实、改写解释、补充自己的理解、审阅图是否准确），并建议把核查记录写进 README。

## 四、输出结构（八个板块，缺一不可，顺序固定）

### 板块 1：学习目标（3–5 条）

学完这份资料后应能回答的具体问题，每条以**可检验动词**开头，例如：
- "能说出 XX 的定义"
- "能区分 XX 与 YY 的关键差异"
- "能解释 XX 机制中 A → B 的因果"
- "能举出一个 XX 的具体应用场景"
- "能判断下列说法是否正确：……"

> **自检要点**：动词必须可观察，不能用"了解 / 认识 / 熟悉"等模糊词。

### 板块 2：核心问题（2–3 个）

直击概念本质的问题，**先问后学**，引导读者带着问题读正文。问题的设计要：
- 第 1 个：定义性问题（"它是什么？不是什么？"）
- 第 2 个：机制性问题（"它内部是怎么运转的？"）
- 第 3 个（可选）：边界性问题（"什么时候用它 / 不用它？"）

### 板块 3：通俗解释（150–250 字，含类比）

**写作人称**：第三人称、教学式语言（**不是"我的理解 / 我觉得"这类第一人称口吻**——本资料代表概念本身，不是个人意见）。

**结构**：
1. **一句话定义**（20–40 字，不堆砌术语）
2. **类比**（必须，明确标注"类比："）—— 选一个学习者熟悉的事物做映射，说明"像 X 的 Y"；
3. **类比的局限**（必须）—— 明确写出"但有几点不像：……"，避免读者把类比当事实；
4. **关键特征**（3–5 个短句，每句 ≤ 20 字）。

> **自检要点**：类比必须紧跟"局限说明"；禁止使用"也许 / 大概 / 我觉得"等模糊措辞。

### 板块 4：核心机制 / 组成（必配 1 张可视化图）

把概念拆解为 3–5 个组成部分或运行机制：

1. **机制拆解**：每个机制用 1–2 句话讲清"做什么 / 为什么需要它"；
2. **机制图**：按"可视化规范"选 1 张 Mermaid 图（流程图 / 时序图 / 概念图 / 思维导图），节点文字 ≤ 6 汉字；
3. **图后解读**（2–4 句）：说明图的阅读顺序、关键节点含义、把图映射回正文；
4. **对比表**（如果机制维度多）：用表格压缩信息，避免图过载。

### 板块 5：应用场景（必配 1 张可视化图）

一个**具体、可想象、与学习者生活贴近**的场景：

1. **场景描述**：用 1 段话讲清"谁在什么情况下要做什么"；
2. **发挥作用的可视化图**：Mermaid 时序图（多角色交互）或流程图最佳，按步骤走一遍；
3. **图后解读**：把场景拆成 N 步，依次对应图中的节点 / 消息。

### 板块 6：概念辨析（含易混淆与使用边界）

**必须**包含三部分：

1. **易混淆对比表**（与 2–3 个近义概念对比）：
   - 维度：定义 / 关注点 / 适用场景 / 常见误用
   - 至少 3 行 × 4 列
2. **常见误解清单**（3–5 条，每条 "误解 X → 正确认识 Y" 的对照格式）
3. **使用边界**（明确写出"什么时候该用 / 不该用"）

> **自检要点**：易混淆的"易"来自学习者常见混淆点，不是为了凑数；不能与本概念毫无关系的概念强行对比。

### 板块 7：自测问题（题型明确 + 答错反馈）

**题型配比**（5 题）：
- **单选题**：3 道（4 选 1，题干明确，干扰项反映常见误解）
- **简答题**：2 道（30–80 字回答，覆盖应用与机制）

**答案区结构**（必须三段）：
1. **正确答案**（一句话）
2. **答错反馈**（如果是选择题："你可能误选了 X，原因是 Y；正确思路是 Z"；如果是简答："得分点：① …… ② …… ③ ……；常见漏答：……"）
3. **回到正文**：指出答案对应哪个板块、哪段论述

**默认折叠**：用 `<details>` 标签包裹答案区域，避免读者先看到答案。

### 板块 8：参考来源（仅官方）

2–4 条真实链接，**仅允许**：
- ✅ 官方文档（vendor docs）
- ✅ 经典论文（arXiv / DOI 论文页）
- ✅ 官方技术百科（如 AWS / IBM / 微软 Learn 的官方百科条目）
- ❌ **明确禁止**：个人博客、Medium 文章、知乎 / CSDN 帖子、第三方教程网站、内容农场

每条标注：
- 来源名称、URL、**访问日期**（YYYY-MM-DD）
- 该来源支撑了资料中的哪部分内容（对应板块编号）

## 四之五、可视化规范

**目的**：让抽象概念"看一眼就懂"，降低理解门槛。

**优先级**：Mermaid 图 > 内联 SVG > ASCII 文本图。Mermaid 写法可读、易维护、AI 写得准、人审得过来。

**配色严格收敛**（与 HTML 整体一致）：
- 主线：`#2563eb`（蓝，仅用于主线 / 主动作）
- 强调：`#b45309`（橙，仅用于强调点 / 反例 / 警告）
- 中性：`#475569`（灰，用于标签、辅助文字）
- **禁止**：紫色 / 青色 / 绿色 / 红色等其他语义色——保持资料整体的视觉简洁

**Mermaid 使用规范**：

1. **HTML 末尾引入一次**：
   ```html
   <script src="https://cdn.jsdelivr.net/npm/mermaid@10/dist/mermaid.min.js"></script>
   <script>mermaid.initialize({ startOnLoad: true, theme: 'neutral', securityLevel: 'loose' });</script>
   ```
   `<head>` 加 meta 标注"含 Mermaid 图表，离线时显示源代码"。

2. **每张图用 `<pre class="mermaid">...</pre>` 包裹**，代码块本身即可读（不渲染时也能看懂）。

3. **可用图类型与典型场景**：

   | 图类型 | Mermaid 语法 | 典型场景 |
   |--------|---------------|----------|
   | **时序图** | `sequenceDiagram` | 多角色交互（用户↔Agent↔工具） |
   | **流程图** | `flowchart LR/TD` | 单线流程（RAG 三阶段、上下文填充） |
   | **状态图** | `stateDiagram-v2` | 状态机（Skill 加载触发、上下文窗口裁剪） |
   | **概念图** | `graph LR` + 节点连线 | 概念间关系网 |
   | **思维导图** | `mindmap` | 概念的组成维度 |

4. **写法要求**：
   - 节点文字 **≤ 6 个汉字**（或 3 个英文单词），长文字拆节点；
   - 箭头方向**有明确语义**：实线 = 数据 / 控制流，虚线 = 反馈 / 迭代；
   - 关键节点用粗框 / classDef 高亮突出主线；
   - 配色仅用蓝 / 橙 / 灰三色，与 HTML 整体一致。

5. **降级方案**：CDN 不可用时，图块显示原始 Mermaid 代码（仍可读懂）；**永远不要把信息只藏在图里**——表格或文字说明必须紧随其后。

6. **每个 Mermaid 图后必须配 2–4 句文字解读**，避免"图归图文归文"。

**何时不用图**：概念极简单（如"整数"）、表格已足够、节点数 > 10 时应拆图或改表。

## 五、资料来源要求

- **只允许**以下来源类型：
  - ✅ 官方文档（vendor docs）：如 `docs.anthropic.com`、`platform.openai.com`、`learn.microsoft.com`
  - ✅ 经典论文：arXiv 论文页（`arxiv.org/abs/xxxx`）、DOI 链接、官方期刊页
  - ✅ 官方技术百科：如 AWS / IBM / 微软 Learn / NVIDIA 官方百科条目（**注意**：必须是这些厂商官方域名的百科页面，不是博客）
- **明确禁止**：
  - ❌ 个人博客（包括工程师个人博客、Medium 文章、Substack）
  - ❌ 第三方教程网站（如教程聚合站、个人教学站点）
  - ❌ 知乎 / CSDN / 掘金 / 简书 等 UGC 内容平台
  - ❌ 内容农场、SEO 站
- 每条来源**生成前必须实际访问验证**（HTTP 200 且内容相关）
- 每条来源标注访问日期（YYYY-MM-DD）
- **禁止编造**论文、作者、URL、数据；禁止把"听说"写成"事实"
- 不同来源说法冲突时，以官方文档为准
- 来源数量不足 2 个时，宁可暂停并向用户说明，也不要用博客等非官方来源补

- 第 4、5 板块各 1 张 Mermaid 图，配色蓝 / 橙 / 灰

## 八、使用经验与迭代记录

本节记录 Skill 在实际使用中发现的新约束或更好的做法。后续每次使用后，建议追加一条。

- **2026-09-04 RAG 应用经验**：
  1. 在生成"和已有概念强相关"的概念（如 RAG ↔ 上下文、Agent ↔ Skill）时，应在板块 3 中**显式回链**到已有概念（指向已生成的 HTML 文件名），让概念网络逐步长出来，而不是各管各的散点；
  2. 当使用方处于受限网络（频繁 502）时，**生成阶段不要试图访问网络**——来源验证可在生成前用 `curl` 一次性批量跑完并保存本地清单，避免 8 个来源逐个 502 把生成流程拖垮；
  3. 「自测问题」的"易混题"答案应写得**比教材还直白**，因为用户常在答错后才来对答案，参考答案的"可读性"比"严谨性"更优先；
  4. 每次使用后，把新发现的规则直接追加到本节，让 Skill 越用越聪明——这正是 Skill 的核心价值：**把一次性的好做法沉淀成可复用的方法论**。

- **2026-09-10 可视化经验**：
  1. **Mermaid 取代 SVG 优先**：手写 SVG 改一处要重画整张图，维护成本高；Mermaid 文字描述图结构，可 diff、可复用、AI 写得准人也审得过来；
  2. **节点文字必须短**：第一版常把整段话塞进一个节点，结果图变"墙"；正确做法是节点只放关键词 + 旁边表格补全细节；
  3. **图后必跟解读**：图说明的是结构，解读说明的是含义；两者缺一就会"图归图文归文"；
  4. **CDN 不可用是常态，不是异常**：用 `<pre class="mermaid">` 包裹让 CDN 失败时显示源代码即可——这就是为什么"信息不能只藏在图里"；
  5. **可视化不等于好看**：判断标准是"看完图比看完正文更快理解结构"，不是"图漂亮"；节点数 > 10 时应拆成多图或改用表格。

- **2026-09-10 可视化落地记录**（上面 5 条规则的执行验证）：
  1. 把 5 份资料的"应用场景"板块各补 1 张 Mermaid 时序图，配 2-4 句图后解读；
  2. 选型：时序图优先于流程图——Agent、上下文、Skill、RAG 都是多角色交互，"谁什么时候做了什么"用时序图最直观；
  3. `<head>` 加一次性 Mermaid CDN 引入，CDN 不可达时图表块显示源代码而非空白；
  4. CSS 加 `.figure` / `.mermaid` / `.mermaid-legend` 三类样式，让图块有边框、有图题、有解读区；
  5. 第 4 板块原有 SVG 机制图保留不动（已满足"至少配 1 张可视化图"的硬性要求）；
  6. **自检清单强化**：本节新增的规则应同步写进第六节「自检清单」，避免 Skill 文档与执行脱节。

- **2026-09-10 第二轮 Skill 迭代（用户反馈驱动）**：
  1. **板块 3 改名"通俗解释"，去掉第一人称口吻**：原"我的理解：xxx"是个反模式——本资料代表概念本身，不是个人意见；改为第三人称、教学式语言，更适合作为学习材料被他人引用；
  2. **强化"类比"为板块 3 的强制要素**：类比 + 类比局限是新学习者最容易理解、又最容易误用的工具，必须显式标注；
  3. **来源类型收紧为仅官方**：原"知名工程师博客"虽质量不错，但带来两个问题——一是博客观点不等于事实，二是个人博客容易 404 / 内容农场化。改为"官方文档 / arXiv 论文 / 官方百科"三类，对应"权威 + 可核查 + 持久"三个特性；
  4. **配色严格收敛到 2 语义色 + 中性灰**：原版用 5 色（蓝 / 紫 / 橙 / 青 / 绿），信息层清晰但视觉嘈杂；改为蓝（主线）+ 橙（强调）+ 灰（中性），与 Mermaid 图配色保持一致，资料整体更耐读；
  5. **板块 7 自测新增"答错反馈"机制**：原版只给正确答案，答错的人不知道为什么错。新结构每个答案分三段——正确答案 + 答错反馈（"你可能误选 X，因为 Y；正确思路是 Z"）+ 回到正文（指明答案对应哪个板块），让错题本身成为学习机会；
  6. **板块 7 题型明确为 3 单选 + 2 简答**：选择题适合检验"概念辨析"，简答题适合检验"应用与机制"，两类题型互补覆盖板块 4、5、6 的核心知识点；
  7. **板块 6 强化为"易混淆对比表 + 常见误解清单 + 使用边界"三件套**：原版只有对比表，易混淆的"易"被简化了；增加"常见误解"使学习者提前避开坑，"使用边界"明确"什么时候不该用"；
  8. **板块 1 学习目标改用可检验动词**：原版允许"了解 / 认识"等模糊词，导致"目标"形同虚设；改为"说 / 区分 / 解释 / 举出 / 判断"等可观察动词，让学习目标真正可被验证；
  9. **自检清单升级为分组（结构 / 可视化 / 来源 / 输出）**：原版平铺一段，难以快速过审；分组后人工核查时可按段打勾，减少漏检；
  10. **本次迭代本身的方法论**：用户的修改要求拆为 7 条独立诉求，先列对照表确认理解一致，再整体重写 Skill 文档——这种"先对齐再改"的工作流值得下次沿用。
